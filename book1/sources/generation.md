## Sourced claims

### A. Generation as a loop, and its two phases

### GN1. Generation is next-token prediction run in a loop with a "decoding strategy"
- Source: `holtzman2020curious`
- Location: p. 3.
- Quote: "given a sequence of m tokens x1 . . . xm as context, the task is to generate the next n continuation tokens to obtain the completed sequence x1 . . . xm+n . We assume that models compute P (x1:m+n ) using the common left-to-right decomposition of the text probability" (Eq. 1, the product of P(xi | x1 . . . xi-1)) "which is used to generate the generation token-by-token using a particular decoding strategy." (the doubled "generate the generation" is in the source).
- Also: GPT-3 "an autoregressive language model" (`brown2020language` p. 1, already used in `destination`); the chain rule for text probability is in `destination` (citing `radford2019language` p. 2). Kwon et al. call the factorization the "autoregressive decomposition" (`kwon2023efficient` p. 3).
- Note: the destination chapter already has "append and repeat". This chapter's new word is **decoding strategy** (or decoding method): the rule that turns each next-token distribution into a choice. Holtzman et al.'s own terms are "maximization-based decoding" and "stochastic decoding".

### GN2. Directed versus open-ended generation
- Source: `holtzman2020curious`
- Location: p. 3.
- Quotes: "Many text generation tasks are defined through (input, output) pairs, such that the output is a constrained transformation of the input. Example applications include machine translation ..., data-to-text generation ..., and summarization ... We refer to these tasks as directed generation." "Generation is usually performed using beam search; since output is tightly scoped by the input, repetition and genericness are not as problematic." "Open-ended generation, which includes conditional story generation and contextual text continuation ... While the input context restricts the space of acceptable output generations, there is a considerable degree of freedom in what can plausibly come next". "some tasks, such as goal-oriented dialog, may fall somewhere in between open-ended and directed generation."
- Note: the key to the beam search story (GND1). A chat assistant's reply sits between the two, in the authors' own words about dialog.

### GN3. Prefill and decode: the prompt is read in parallel, the reply is written one token at a time
- Sources: `pope2022efficiently`, `kwon2023efficient`, `grattafiori2024llama`, `anthropic2026glossary`.
- Pope et al., p. 2: "The latency is the total time for an inference and can be broken down into the time to process the input tokens present at the start of the inference (which we call "prefill") and the time to autoregressively generate output tokens (which we term "decode")." p. 3: "Since the input tokens are all present at the start of the inference, we can run the model over all B x Linput many tokens in parallel, in a single forwards pass over all the tokens. We call this step prefill. The output tokens are generated autoregressively, with a sequential loop of Lgen steps. Each step consists of a single forwards pass through the model, after which we sample one new token for each of the B examples in the batch. This loop is known as generation or decode." p. 1: "generative inference proceeds one token at a time and the computation for each token sequentially depends on the previously generated tokens."
- Kwon et al., p. 3: "The prompt phase takes the whole user prompt (x1, ..., xn) as input and computes the probability of the first new token ... Since prompt tokens x1, ..., xn are all known, the computation of the prompt phase can be parallelized using matrix-matrix multiplication operations." "The autoregressive generation phase generates the remaining new tokens sequentially." "The computation at different iterations cannot be parallelized due to the data dependency and often uses matrix-vector multiplication, which is less efficient. As a result, this phase severely underutilizes GPU computation and becomes memory-bound, being responsible for most portion of the latency of a single request."
- Llama 3, Fig. 24 (p. 52): axis labels "Prefill Latency (time-to-first-token, ms)" and "Decode Latency (time-to-incremental-token, ms)"; caption "Effect of micro-batching on inference throughput and latency during the Left: pre-filling and Right: decoding stage." p. 52 also: "the key-value cache pre-fill stage of inference and ... the decoding stage".
- Anthropic glossary (as of 2026-11): "Time to first token (TTFT) is a performance metric that measures the time it takes for a language model to generate the first token of its output after receiving a prompt."
- Note: the reader-facing version: "reading your message" is fast per token because all its tokens go through the network together; "writing the reply" is slow per token because each token needs the one before it. This is why a chat reply streams out word by word after a short pause. The terms prefill, decode, and time to first token are worth defining (the reader will meet them on model cards and runtime screens). Seq2seq's Q21 note ("generation is word by word for any model") is the hand-off.

### GN4. Decoding is slow because of memory traffic, not arithmetic
- Sources: `shazeer2019fast`, `pope2022efficiently`, `kwon2023efficient`, `chen2023accelerating`, `leviathan2023fast`.
- Shazeer, abstract (p. 1): "While training these layers is generally fast and simple, due to parallelizability across the length of the sequence, incremental inference (where such paralleization is impossible) is often slow, due to the memory-bandwidth cost of repeatedly loading the large "keys" and "values" tensors." (sic "paralleization"). p. 3: on GPU/TPU hardware "the computational capacity can be two orders of magnitude higher than the memory bandwidth." p. 4: when the sequence length is close to the model dimension or the batch is about 1, "the ratio is close to 1, causing memory bandwidth to be a major performance bottleneck on modern computing hardware."
- Shazeer, measured times (p. 7; one TPUv2 with 8 cores; an encoder-decoder translation model; batch of 1024 sequences, 128 source and 128 target tokens; greedy decoding): baseline "the encoder part of the model took 222ms and each incremental step of the decoder took 47ms ... the amortized inference time is 1.7µs per token for the encoder and a much larger 46µs per token for the decoder". Multi-query model: "the encoder took 195ms and the decoder took 3.9ms per step, for amortized per-token costs of 1.5µs and 3.8µs respectively."
- Pope et al., p. 1: "The large memory footprint gives rise to a large amount of memory traffic to load the parameters and KV cache from high-bandwidth memory (HBM) into the compute cores for each step". p. 3: "At small batch sizes and sequence lengths, the time to load weights dominates. At larger batch sizes and sequence lengths (e.g. 2048+ tokens with batch size 512+), the time to load the KV cache dominates."
- Chen et al., p. 1: "Transformer sampling is typically memory bandwidth bound (Shazeer, 2019), so for a given set of hardware, the time to generate a single token in transformer models is proportional to a first order approximation to the size of parameters and the size of the transformer memory." Leviathan et al., p. 1: "inference from large models is often not bottlenecked on arithmetic operations, but rather on memory bandwidth and communication".
- Note: the bridge for a 2000s reader: the processor spends most of a decode step waiting for the weights to arrive from memory, then does a little arithmetic on one token. Shazeer's 1.7 vs 46 microseconds (encoder reading in parallel vs decoder writing one step at a time; about 27 times) is the cleanest printed number, but it is an encoder-decoder translation model of 2019, amortized over a batch of 1024: say so. Do not generalize the ratio.

### B. Choosing a token: decoding methods

### GN6. Greedy decoding in practice
- Sources: `radford2019language`, `he2025defeating`, `holtzman2020curious`.
- GPT-2 used greedy decoding for some evaluations: p. 6, "Greedy decoding from GPT-2 when conditioned on a document, the history of the associated conversation, and a final token A: achieves 55 F1 on the development set" (CoQA); for translation, "we sample from the model with greedy decoding and use the first generated sentence as the translation" (p. 6). Summarization used "Top-k random sampling (Fan et al., 2018) with k = 2 which reduces repetition and encourages more abstractive summaries than greedy decoding" (p. 6).
- Thinking Machines (sidenote on "temperature down to 0"): "This means that the LLM always chooses the highest probability token, which is called greedy sampling."
- Holtzman et al., Table 1 (p. 7): Greedy has perplexity 1.50 and Repetition 73.66%, against Human 12.38 and 0.28% (see GN9).
- Note: define **greedy decoding** as "always take the most probable token" (the destination chapter's "simplest rule"). Its weakness for open-ended text is in GN9.

### GN7. Beam search, and its use for directed tasks through 2020
- Sources: `sutskever2014sequence` (existing; via `seq2seq`), `brown2020language`, `shazeer2019fast`, `holtzman2020curious`, `kwon2023efficient`.
- GPT-3, p. 10: "On tasks with free-form completion, we use beam search with the same parameters as [RSR+19]: a beam width of 4 and a length penalty of α = 0.6." ([RSR+19] is the T5 paper; not fetched.)
- Shazeer (p. 7) validated translation results "using both greedy decoding and beam search (beam 4, α = 0.6)".
- Holtzman et al., p. 4: "Since finding the optimum argmax sequence from recurrent neural language models or Transformers is not tractable (Chen et al., 2018), common practice is to use beam search". p. 3: for directed generation, "Generation is usually performed using beam search".
- Kwon et al., p. 4: "In more sophisticated algorithms like beam search [49], different request beams can share larger portions (up to 55% memory saving ...)" (as of 2023, beam search still offered by serving systems).
- Note: beam search was defined in `seq2seq` ("kept the few best partial translations"). Here say only what is new: that "the best sequence" cannot be found exactly by checking every possibility, so beam search approximates it, and that it stayed standard for tasks with one right answer (translation; GPT-3's question answering in 2020). A "length penalty" is a correction for beam search's preference for short outputs (GN10); define it in one clause if mentioned at all.

### GN8. Beam search failures in translation: the most probable output is often empty
- Source: `stahlberg2019nmt`.
- Location: p. 3356 (abstract).
- Quote: "We use our exact search to find the global best model scores under a Transformer base model for the entire WMT15 English-German test set. Surprisingly, beam search fails to find these global best model scores in most cases, even with a very large beam size of 100. For more than 50% of the sentences, the model in fact assigns its global best score to the empty translation, revealing a massive failure of neural models in properly accounting for adequacy. We show by constraining search with a minimum translation length that at the root of the problem of empty translations lies an inherent bias towards shorter translations. We conclude that vanilla NMT in its current form requires just the right amount of beam search errors, which, from a modelling perspective, is a highly unsatisfactory conclusion indeed, as the model often prefers an empty translation."
- Holtzman et al. cite this (p. 3): issues reported "more recently with exact inference (Stahlberg & Byrne, 2019), a counter-intuitive observation since more comprehensive search helps maximize probability."
- Note: a striking, checkable fact that makes the abstract point concrete: multiplying many probabilities below 1 favors short outputs (see mechanism item 7). Keep to one paragraph; it is about a 2019 translation model, not LLMs.

### GN9. Holtzman et al. (2019-2020): maximization produces degenerate text
- Source: `holtzman2020curious`.
- Abstract (p. 1): "The counter-intuitive empirical observation is that even though the use of likelihood as training objective leads to high quality models for a broad range of language understanding tasks, maximization-based decoding methods such as beam search lead to degeneration - output text that is bland, incoherent, or gets stuck in repetitive loops." (source prints an em-dash before "output"). Results: "(1) maximization is an inappropriate decoding objective for open-ended text generation, (2) the probability distributions of the best current language models have an unreliable tail which needs to be truncated during generation and (3) Nucleus Sampling is currently the best available decoding strategy for generating long-form text that is both high-quality - as measured by human evaluation - and as diverse as human-written text." (em-dashes in source).
- Fig. 1 (p. 1): prompt about unicorns in the Andes; "Beam Search, b=32" repeats "Universidad Nacional Autónoma de México" in a loop; caption: "Even with substantial human context and the powerful GPT-2 Large language model, Beam Search (size 32) leads to degenerate repetition (highlighted in blue) while pure sampling leads to incoherent gibberish (highlighted in red). When b ≥ 64, both GPT-2 Large and XL (774M and 1542M parameters, respectively) prefer to stop generating immediately after the given context."
- p. 2: "language models do generally assign high scores to well-formed text, yet the highest scores for longer texts are often generic, repetitive, and awkward."
- Setup (p. 6): GPT-2 Large; "Our analysis is based on generating 5,000 text passages, which end upon reaching an end-of-document token or a maximum length of 200 tokens", conditioned on 1-40-token openings of held-out WebText documents.
- Table 1 (p. 7, layout extraction), columns Perplexity / Self-BLEU4 / Zipf / Repetition % / HUSE: Human 12.38 / 0.31 / 0.93 / 0.28 / -; Greedy 1.50 / 0.50 / 1.00 / 73.66 / -; Beam, b=16 1.48 / 0.44 / 0.94 / 28.94 / -; Stochastic Beam, b=16 19.20 / 0.28 / 0.91 / 0.32 / -; Pure Sampling 22.73 / 0.28 / 0.93 / 0.22 / 0.67; Sampling, t=0.9 10.25 / 0.35 / 0.96 / 0.66 / 0.79; Top-k=40 6.88 / 0.39 / 0.96 / 0.78 / 0.19; Top-k=640 13.82 / 0.32 / 0.96 / 0.28 / 0.94; Top-k=40, t=0.7 3.48 / 0.44 / 1.00 / 8.86 / 0.08; Nucleus p=0.95 13.13 / 0.32 / 0.95 / 0.36 / 0.97.
- Repetition is defined (Fig. 9 caption, p. 9): "A phrase (minimum length 2) is considered a repetition when it repeats at least three times at the end of the generation."
- Note: the perplexity column is the model's perplexity on its own generated text (p. 6), the measure from `prediction`. Greedy and beam text is far more predictable than human text (1.5 vs 12.4): that is the numerical form of "bland". Pure sampling is less predictable than human text (22.7). The chapter can print a small subset of Table 1 (Human, Greedy, Beam, Pure sampling, Nucleus) with the perplexity and repetition columns.

### GN10. The repetition loop reinforces itself
- Source: `holtzman2020curious`.
- Fig. 4 (p. 5), title on the image: "Token Probabilities for "I don't know." Repeated 200 times". Caption: "The probability of a repeated phrase increases with each repetition, creating a positive feedback loop. We found this effect to hold for the vast majority of phrases we tested, regardless of phrase length or if the phrases were sampled randomly rather than taken from human text."
- Also Fig. 2 caption (p. 2): "The probability assigned to tokens generated by Beam Search and humans, given the same context. Note the increased variance that characterizes human text, in contrast with the endless repetition of text decoded by Beam Search."
- Fan et al. saw the same in 2018 (p. 896, section on limitations): "A further obstacle is repetition. The model focuses frequently on what it has recently produced".
- Note: the mechanism for the reader: once a phrase is in the context, the model (trained on text where things that appeared often appear again) rates it more likely next time; greedy decoding always takes it, so the loop closes. Do not reproduce the figure's curve as numbers [D-009]; describe it.

### GN11. Human text is not the most probable text
- Source: `holtzman2020curious`.
- Location: p. 7, section 4.3 "Natural Language Does Not Maximize Probability".
- Quotes: "One might wonder if the issue with maximization is a search error, i.e., there are higher quality sentences to which the model assigns higher probability than to the decoded ones, beam search has just failed to find them. Yet Figures 2 & 6 show that the per-token probability of natural text is, on average, much lower than text generated by beam search. Natural language rarely remains in a high probability zone for multiple consecutive time steps, instead veering into lower-probability but more informative tokens." "Why is human-written text not the most probable text? We conjecture that this is an intrinsic property of human language." "Grice's Maxims of Communication (Grice, 1975) show that people optimize against stating the obvious. Thus, making every word as predictable as possible will be disfavored."
- Note: the authors call the explanation a conjecture; say so. Bridge to `prediction`: Shannon's game showed misses cluster where "the line of thought has more possibility of branching out"; informative text is surprising text. This is the heart of the chapter's argument for sampling.

### GN12. Pure sampling and the "unreliable tail"
- Source: `holtzman2020curious`.
- p. 2: "pure sampling - sampling directly from the probabilities predicted by the model - results in text that is incoherent and almost unrelated to the context." (em-dashes in source). "This unreliable tail is composed of tens of thousands of candidate tokens with relatively low probability that are over-represented in the aggregate." p. 6: "perplexity of text obtained from pure sampling is worse than the perplexity of the gold. This indicates that the model is confusing itself: sampling too many unlikely tokens and creating context that makes it difficult to recover the human distribution of text". p. 10: full sampling invented "a new word "umidauda", apparently a species of bird."
- Fan et al. (p. 894): "Completely random sampling can introduce very unlikely words, which can damage generation as the model has not seen such mistakes at training time."
- Note: the arithmetic behind "over-represented in the aggregate": many tokens each with tiny probability can together hold a large share. The destination toy ("dog" 1%, "the" 0.4%) is too small to show this; mechanism item 5 builds a version with a long tail. Pure sampling is what `destination`'s ruler draw does.

### GN13. Top-k sampling (Fan et al. 2018; GPT-2 2019)
- Sources: `fan2018hierarchical`, `radford2019language`, `holtzman2020curious`.
- Fan et al., p. 893 (section 5.4): "We generate stories from our models using a top-k random sampling scheme. At each timestep, the model generates the probability of each word in the vocabulary being the likely next word. We randomly sample from the k = 10 most likely candidates from this distribution. We find this sampling strategy substantially more effective than beam search, which tends to produce common phrases and repetitive text from the training set". p. 894: "Sentences produced by beam search tend to be short and generic." - GPT-2: Tables 7-10 captions (pp. 14-17): "Contexts are 768 tokens, with approximately 256 tokens worth of paragraphs shown. Completions are 256 tokens and fully shown. Then "re-scaled as in equation 3": the kept probabilities are divided by their sum. ### GN14. Nucleus (top-p) sampling
- Source: `holtzman2020curious`.
- Location: pp. 4-6.
- Definition (p. 4): "Given a distribution P (x|x1:i-1), we define its top-p vocabulary V(p) ⊂ V as the smallest set such that" the probabilities in it sum to at least p (Eq. 2). p. 5: "The original distribution is re-scaled to a new distribution, from which the next word is sampled" (Eq. 3: divide by the kept total p'; zero outside). "In practice this means selecting the highest probability tokens whose cumulative probability mass exceeds the pre-chosen threshold p. The size of the sampling set will adjust dynamically based on the shape of the probability distribution at each time step. For high values of p, this is a small subset of vocabulary that takes up vast majority of the probability mass - the nucleus." (em-dash in source).
- Why not a fixed k (pp. 5-6, with Fig. 5 "Flat Distribution" vs "Peaked Distribution"): "in some contexts the head of the next word distribution can be flat across tens or hundreds of reasonable options (e.g. nouns or verbs in generic contexts), while in other contexts most of the probability mass is concentrated in one or a small number of tokens ... Therefore if k is small, in some contexts there is a risk of generating bland or generic text, while if k is large the top-k vocabulary will include inappropriate candidates which will have their probability of being sampled increased by the renormalization." p. 2: the nucleus is "a small subset of the vocabulary that tends to range between one and a thousand candidates."
- Usual values (Fig. 9 caption, p. 9): "values of p are usually in [0.9, 1)". Results: Nucleus p = 0.95 had the highest HUSE score, 0.97 (Table 1, p. 7; "Nucleus Sampling obtains the highest HUSE score, with Top-k sampling performing second best", p. 10). HUSE: a combined human and statistical score; "For each decoding algorithm we annotate 200 generations for typicality, with each generation receiving 20 annotations from 20 different annotators" (p. 9).
- Note: name both "nucleus sampling" and "top-p" (the vendor parameter is `top_p`, GN19). HUSE is a niche measure; the chapter can say "a combined human and statistical evaluation" and give the ranking, not the numbers. Results are for GPT-2 Large in 2019; date-stamp.

### GN15. Temperature: definition in the generation literature
- Source: `holtzman2020curious`.
- Location: p. 6, section 3.3.
- Quotes: "Another common approach to sampling-based generation is to shape a probability distribution through temperature (Ackley et al., 1985). Temperature sampling has been applied widely to text generation (Ficler & Goldberg, 2017; Fan et al., 2018; Caccia et al., 2018). Given the logits u1:|V| and temperature t, the softmax is re-estimated as" p(x = Vl | x1:i-1) = exp(ul / t) / Σl' exp(ul' / t) (Eq. 4). "Setting t ∈ [0, 1) skews the distribution towards high probability events, which implicitly lowers the mass in the tail distribution. Low temperature sampling has also been used to partially alleviate the issues of top-k sampling discussed above, by shaping the distribution before top-k sampling ... However, recent analysis has shown that, while lowering the temperature improves generation quality, it comes at the cost of decreasing diversity". Fig. 9 caption (p. 9): "Sampling with temperatures lower than 0.9 severely increase repetition." p. 10: "When top-k sampling is combined with a temperature of 0.7, as is commonly done (Radford et al., 2019; Fan et al., 2018), the output devolves into repetition, exhibiting the classic issues of low-temperature decoding." (see GND4 on the attribution).
- Note: this is the formula for the chapter: the destination's softmax with every score divided by T first. It is a standard form [D-002]. Temperature does not change which token is most probable (mechanism item 2), so it has no effect on greedy decoding.

### GN16. Temperature in a softmax, in the deep-learning literature (2015)
- Source: `hinton2015distilling`.
- Location: pp. 2-3.
- Quotes: p. 2: "Neural networks typically produce class probabilities by using a "softmax" output layer that converts the logit, zi, computed for each class into a probability, qi, by comparing zi with the other logits." Eq. (1): qi = exp(zi/T) / Σj exp(zj/T); p. 3: "where T is a temperature that is normally set to 1. Using a higher value for T produces a softer probability distribution over classes." p. 2: "Our more general solution, called "distillation", is to raise the temperature of the final softmax until the cumbersome model produces a suitably soft set of targets."
- Note: the cleanest statement of "temperature 1 is the plain softmax; higher is softer". Distillation itself belongs to `adapting`; mention only the definition here.

### GN17. Where the word comes from: Boltzmann machines and statistical physics (1985)
- Source: `ackley1985learning`.
- Location: pp. 151-152.
- Quotes (p. 151, read on the page image): "A simple way to get out of local minima is to occasionally allow jumps to configurations of higher energy. An algorithm with this property was introduced by Metropolis, Rosenbluth, Rosenbluth, Teller, & Teller (1953) to study average properties of thermodynamic systems (Binder, 1978) and has recently been applied to problems of constraint satisfaction (Kirkpatrick, Gelatt, & Vecchi, 1983)." Eq. (5): a unit turns on with probability pk = 1 / (1 + e^(-ΔEk/T)), "where T is a parameter that acts like temperature (see Figure 1)." Fig. 1 caption: "Eq. (5) at T=1.0 (solid), T=4.0 (dashed), and T=0.25 (dotted)." p. 152: "A system of such particles in contact with a heat bath at a given temperature will eventually reach thermal equilibrium and the probability of finding the system in any global state will then obey a Boltzmann distribution." Eq. (6): Pα / Pβ = e^(-(Eα - Eβ)/T). "At low temperatures there is a strong bias in favor of states with low energy, but the time required to reach equilibrium may be long. At higher temperatures the bias is not so favorable but equilibrium is reached faster. A good way to beat this trade-off is to start at a high temperature and gradually reduce it. This corresponds to annealing a physical system (Kirkpatrick, Gelatt, & Vecchi, 1983)."
- Note: two honest bridges. (1) Eq. (5) is the logistic function of the reader's logistic regression, with the input divided by T; Fig. 1 shows the curve going steep at T = 0.25 and flat at T = 4. (2) A reader who knows simulated annealing knows this T already: the Boltzmann distribution gives each state a probability proportional to e^(-energy/T); with "score" for minus energy, that is exactly the softmax with temperature. Holtzman et al. cite Ackley et al. as the source of temperature for sampling (GN15). Do not claim Ackley et al. used temperature for text; they did not. The statistical-physics origin (Boltzmann, Metropolis) is background known here only through this paper.

### GN22. Sampling is the reason; temperature 0 removes it in principle

### GN23. But real systems are not deterministic even at temperature 0 (an attributed account)
- Sources: `he2025defeating`; `anthropic2026glossary`, `anthropic2026opus55migration`, `openai2026chatcreate` (GN19, GN20) as vendor statements.
- Thinking Machines: "even when we adjust the temperature down to 0 ... LLM APIs are still not deterministic in practice". Common explanation: "One common hypothesis is that some combination of floating-point non-associativity and concurrent execution leads to nondeterminism based on which concurrent core finishes first. We will call this the "concurrency + floating point" hypothesis". Their finding: "our request's output does depend on the parallel user requests. Not because we're somehow leaking information across batches - instead, it's because our forward pass lacks "batch invariance", causing our request's output to depend on the batch size of our forward pass." (em-dash in source). "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies!" Root numerical cause: "floating-point non-associativity", (a + b) + c ≠ a + (b + c).
- Experiment: "We use Qwen/Qwen3-235B-A22B-Instruct-2507 and sample 1000 completions at temperature 0 with the prompt "Tell me about Richard Feynman" (non-thinking mode), generating 1000 tokens each. Surprisingly, we generate 80 unique completions, with the most common of these occuring 78 times." (sic "occuring"). "the completions are actually identical for the first 102 tokens! The first instance of diverging completions occurs at the 103rd token. All completions generate the sequence "Feynman was born on May 11, 1918, in" However, 992 of the completions go on to generate "Queens, New York" whereas 8 of the completions generate "New York City"." "when we enable our batch-invariant kernels, all of our 1000 completions are identical." Cost: on one GPU running Qwen-3-8B, 1000 sequences took 26 s with default vLLM, 55 s "Unoptimized Deterministic vLLM", 42 s with an improved attention kernel.
- Note: present as an attributed account ("researchers at Thinking Machines reported in September 2025"), and the vendor statements as vendor statements (as of 2026-11). The reader-level explanation: tiny rounding differences change a logit in the last decimal places; when two tokens are nearly tied, the top token can flip, and from then on the text differs. The Feynman example shows exactly that: a near tie at token 103. See GND6.

### GN25. The context window as working memory; what happens when it is full
- Sources: `anthropic2026glossary`, `anthropic2026contextwindows`, `dai2019transformer`, `radford2019language`, `grattafiori2024llama`, `llamacpp2026server`.
- Anthropic glossary (as of 2026-11): "The "context window" refers to the amount of text a language model can look back on and reference when generating new text. Context windows doc: it includes "all the text a language model can reference when generating a response, including the response itself". "Progressive token accumulation: As the conversation advances through turns, each user message and assistant response accumulates within the context window, and previous turns are preserved completely." Sizes: a list of current Claude models "have a 1M-token context window"; others 200k. When full: "If the input alone already exceeds the model's context window, the API returns a 400 `invalid_request_error` ("prompt is too long") on every model." - Sliding a fixed window (Dai et al. 2019, p. 2980): for a vanilla Transformer language model at evaluation, "at each step, the vanilla model also consumes a segment of the same length as in training, but only makes one prediction at the last position. The model itself never "forgets" gradually: text is either inside the window or absent. `destination` already says the window is the model's whole working memory; this chapter adds the "full" case. ### GN26. Caching earlier computation: the KV cache
- Sources: `pope2022efficiently`, `kwon2023efficient`, `shazeer2019fast`, `dai2019transformer`.
- Pope et al., p. 1: "The attention key and value tensors of each layer, which we refer to as the KV cache, must also be stored in memory for the duration of decoding." p. 3: "Even though the computational cost of attention is relatively small, it can still account for a significant fraction of memory capacity and bandwidth costs, since (unlike the weights) the KV cache is unique for each sequence in the batch."
- Kwon et al., p. 3: in the generation phase, "Note that the key and value vectors at positions 1 to n + t - 1 are cached at previous iterations, only the new key and value vector kn+t and vn+t are computed at this iteration." p. 1: "these states consist of the key and value tensors associated with the attention mechanism, commonly referred to as KV cache [41], which represent the context from earlier tokens to generate new output tokens in sequence." ([41] is Pope et al.)
- Shazeer (2019), pp. 3-4, section 2.4 "Multihead Attention (Incremental)": "The queries produced at each position attend to key-value pairs produced at all positions up to and including that position. During training, the ground-truth target sequence is known, and we can use an efficient parallel implementation ... However, when generating from the trained model, the output of the self-attention layer at a particular position affects the token that is generated at the next position, which in turn affects the input to that layer at the next position. This prevents parallel computation." The code that follows takes `prev_K` and `prev_V` and returns `new_K` and `new_V` with one more position appended: the cache, in 2019, before the name.
- Dai et al. (2019), p. 2981: with Transformer-XL "during evaluation, the representations from the previous segments can be reused instead of being computed from scratch as in the case of the vanilla model. In our experiments on enwiki8, Transformer-XL is up to 1,800+ times faster than the vanilla model during evaluation". "In theory, we can cache as many previous segments as the GPU memory allows". (This caches hidden states across segments, a related idea, not the decoder KV cache.)
- Note: the reader does not yet know queries, keys, and values (that is `attention`, which comes before this chapter in the outline, so the terms will be available). The plain explanation: each layer computes, for every token, two vectors that later tokens consult (keys and values); these never change once computed, because a token only looks backward; so they are stored and each new token computes only its own. What it saves: re-running the whole prefix through every layer at every step (mechanism item 10). What it costs: memory that grows with every token (GN27). The origin of the technique is not established by any fetched source (GND8).

### GN27. What the KV cache costs in memory
- Sources: `kwon2023efficient`, `pope2022efficiently`, `grattafiori2024llama`, `shazeer2019fast`.
- Kwon et al., p. 4: "for the 13B parameter OPT model [62], the KV cache of a single token demands 800 KB of space, calculated as 2 (key and value vectors) x 5120 (hidden state size) x 40 (number of layers) x 2 (bytes per FP16). Since OPT can generate sequences up to 2048 tokens, the memory required to store the KV cache of one request can be as much as 1.6 GB. Concurrent GPUs have memory capacities in the tens of GBs. Even if all available memory was allocated to KV cache, only a few tens of requests could be accommodated." (checked: 819,200 bytes = 800 KiB; x 2048 = 1.68 GB = 1.56 GiB). p. 1, Fig. 1 (13B model on an NVIDIA A100 40GB): "Approximately 65% of the memory is allocated for the model weights, which remain static during serving. Close to 30% of the memory is used to store the dynamic states of the requests."
- Pope et al., p. 3: "For a 500B+ model with multihead attention, the attention KV cache grows large: for batch size 512 and context length 2048, the KV cache totals 3TB, which is 3 times the size of the model's parameters. The on-chip memory needs to load this KV cache from off-chip memory once for every token generated during which the computational core of the chip is essentially idle." (not reproducible from the paper: GND9).
- Shrinking it: Shazeer's multi-query attention shares one key/value head across all query heads, "greatly reducing the size of these tensors and hence the memory bandwidth requirements of incremental decoding" (abstract, p. 1); Pope et al. p. 6: it "reduces the size of the KV cache tensors by a factor of nheads". Llama 3 (p. 6): "We use grouped query attention (GQA; Ainslie et al. (2023)) with 8 key-value heads to improve inference speed and to reduce the size of key-value caches during decoding." Table 3 (p. 7) for 8B: Layers 32, Model Dimension 4,096, Attention Heads 32, Key/Value Heads 8 (70B: 80 / 8,192 / 64 / 8; 405B: 126 / 16,384 / 128 / 8).
- GPT-2 sizes for a small example: Table 2 (p. 4): 117M: 12 layers, dmodel 768; 1542M: 48 layers, 1600; context 1024 tokens.
- Note: mechanism item 9 does the arithmetic for GPT-2 small and Llama 3 8B. The per-head size 128 for Llama 3 8B is 4,096 / 32, derived, not printed; say so. Grouped-query attention is explained in `since-2017`; here just "Llama 3 keeps 8 key-value heads instead of 32, a quarter of the cache". ### GN29. Speculative decoding (2022-2023): guessing ahead with a small model
- Sources: `leviathan2023fast`, `chen2023accelerating`, `llamacpp2026server`.
- Leviathan et al., abstract (p. 1): "Inference from large autoregressive models like Transformers is slow - decoding K tokens takes K serial runs of the model. In this work we introduce speculative decoding - an algorithm to sample from autoregressive models faster without any changes to the outputs, by computing several tokens in parallel." (dashes as printed are hyphens or em-dashes; check at drafting). "we can make exact decoding from the large models faster, by running them in parallel on the outputs of the approximation models, potentially generating several tokens concurrently, and without changing the distribution." "We demonstrate it on T5-XXL and show a 2X-3X acceleration compared to the standard T5X implementation, with identical outputs." Eq. (1), p. 3 (page image): expected tokens per run of the large model = (1 - α^(γ+1)) / (1 - α), where α is the expected acceptance rate and γ the number of guesses.
- Chen et al., abstract (p. 1): "Our algorithm relies on the observation that the latency of parallel scoring of short continuations, generated by a faster but less powerful draft model, is comparable to that of sampling a single token from the larger target model. This is combined with a novel modified rejection sampling scheme which preserves the distribution of the target model within hardware numerics. We benchmark speculative sampling with Chinchilla, a 70 billion parameter language model, achieving a 2-2.5x decoding speedup in a distributed setup". p. 2: "the work in this manuscript was undertaken concurrently and independently of the work on speculative decoding from Leviathan et al. (2022). ... otherwise the core underlying idea is the same."
- In use (as of 2026-11): llama.cpp's server has options for a draft model, including "how the draft is sampled: greedy takes its argmax, probabilistic samples it and has the target verify by rejection sampling (default: greedy)".
- Note: the idea in a sentence: a small model writes a few tokens ahead; the big model checks them all in one parallel pass (cheap, because checking is like reading a prompt, GN3); accepted tokens are kept, and the first rejected one is replaced by the big model's own choice; the method is arranged so the final text has exactly the big model's probabilities. Keep it to a paragraph; no rejection-sampling details. Mechanism item 12 gives a worked number.

### GN32. Why sampling makes it predictable: decoding randomness and exposure bias
- Source: `ji2023survey`.
- Location: p. 8 (section 3.2).
- Quotes: "the design of the decoding strategy itself can contribute to hallucinations. Dziri et al. [60] illustrate that a decoding strategy that improves the generation diversity, such as top-k sampling, is positively correlated with increased hallucination. We conjecture that deliberately added "randomness" by sampling from the top-k samples instead of choosing the most probable token increase the unexpected nature of the generation, leading to a higher chance of containing hallucinated content." "Exposure Bias. Regardless of decoding strategy choices, the exposure bias problem [13, 213], defined as the discrepancy in decoding between training and inference time, can be another contributor to hallucination. It is common practice to train the decoder with teacher-forced maximum likelihood estimation (MLE) training, where the decoder is encouraged to predict the next token conditioned on the ground-truth prefix sequences. However, during the inference generation, the model generates the next token conditioned on the historical sequences previously generated by itself [97]. Such a discrepancy can lead to increasingly erroneous generation, especially when the target sequence gets longer."
- Note: Ji et al. call the decoding link a conjecture built on one cited study; say so. Exposure bias is a good mechanism for the reader: in training the model always sees real text before each prediction; when generating it sees its own output, including any earlier mistake, and continues it fluently. Kalai et al. list "decoding randomness" among causes cited by others (p. 4) but explicitly say their own analysis "does not rely on properties of next-word prediction" (p. 2): so decoding is one contributor in the literature, not the established root cause (GND2).

### GN33. Kalai et al. (2025): hallucinations as ordinary classification errors, kept by test-style grading
- Source: `kalai2025why`.
- Abstract (p. 1): "Like students facing hard exam questions, large language models sometimes guess when uncertain, producing plausible yet incorrect statements instead of admitting uncertainty." "We argue that language models hallucinate because the training and evaluation procedures reward guessing over acknowledging uncertainty". "Hallucinations need not be mysterious - they originate simply as errors in binary classification. If incorrect statements cannot be distinguished from facts, then hallucinations in pretrained language models will arise through natural statistical pressures." (em-dash in source).
- Pretraining (pp. 2-3): "even if the training data were error-free, the objectives optimized during language model training would lead to errors being generated." The reduction: "(generative error rate) ≳ 2 · (IIV misclassification rate)" (IIV = "Is-It-Valid", a yes/no question of whether a response is valid). Arbitrary facts (p. 3): their analysis "recovers [Kalai and Vempala's] bound that the hallucination rate, after pretraining, should be at least the fraction of training facts that appear once. For instance, if 20% of birthday facts appear exactly once in the pretraining data, then one expects base models to hallucinate on at least 20% of birthday facts."
- Post-training (p. 4): "guessing when unsure maximizes the expected score under a binary 0-1 scheme that awards 1 point for a correct answer and none for blanks or IDKs." "Model B will outperform A under 0-1 scoring, the basis of most current benchmarks."
- Calibration link (p. 8): "Hallucinations are inevitable only for base models. Many have argued that hallucinations are inevitable (Jones, 2025; Leffer, 2024; Xu et al., 2024). However, a non-hallucinating model could be easily created, using a question-answer database and a calculator, which answers a fixed set of questions ... and otherwise outputs IDK. Moreover, the error lower-bound of Corollary 1 implies that language models which do not err must not be calibrated". "calibration - and, hence, errors - is a natural consequence of the standard cross-entropy objective." (em-dashes in source). Fig. 2 (p. 8) reprints GPT-4's calibration plots: "The pretrained model is well calibrated."
- Note: this is the strongest support for the outline's phrase "a predictable property": a model trained to match the frequencies of text (cross-entropy, from `prediction`) must, when it samples, sometimes produce a plausible falsehood, especially for facts it saw once. Attribute it: four authors, three at OpenAI, a 2025 preprint (as of 2026-11 not peer reviewed per the arXiv record). It is an argument, not a consensus. The singleton example is a good reader-level picture: a birthday seen once in training is like a word seen once in an n-gram table (the `prediction` sparsity story).

### GN35. The opposite claim: hallucination is inevitable
- Source: `xu2024hallucination`.
- Abstract (p. 1): "In this paper, we formalize the problem and show that it is impossible to eliminate hallucination in LLMs. Specifically, we define a formal world where hallucination is defined as inconsistencies between a computable LLM and a computable ground truth function. ## Disputed or inconsistent points

### GND1. Is beam search good or bad?
- **Good for directed tasks:** standard for translation and summarization (Holtzman et al. p. 3); GPT-3 used beam width 4 for free-form question answering (p. 10); Shazeer used beam 4 for translation (p. 7); Sutskever et al. 2014 (via `seq2seq`).
- **Bad for open-ended text:** Holtzman et al. (GN9-GN11); Fan et al. p. 893-894 ("common phrases and repetitive text", "short and generic").
- **Even in translation it "works" partly by failing:** Stahlberg and Byrne (GN8): the model's true best is often the empty translation; beam search's search errors hide it.
- Suggested wording: "Searching for the single most probable continuation works well when the task has one right answer, like a translation. For open-ended writing it produces bland, repetitive text, because human writing is not the most probable text. And even in translation, an exact search showed that the model's most probable output was often empty."

### GND2. Is hallucination inevitable, and is sampling the cause?
- **Inevitable in principle:** Xu et al. 2024 (GN35), formal argument.
- **Inevitable for base models, not for systems that may abstain:** Kalai et al. 2025 (GN33, p. 8), who cite Xu et al. as one of those who "have argued that hallucinations are inevitable".
- **Decoding randomness contributes:** Ji et al. p. 8 (a conjecture resting on one cited study); "decoding randomness" also appears in Kalai et al.'s list of others' proposed causes (p. 4).
- **Not about sampling at all:** Kalai et al. p. 2: their analysis "does not rely on properties of next-word prediction or Transformer-based neural networks"; errors arise from the training objective and from grading.
- **The word itself:** GPT-4 System Card footnote 9 (anthropomorphization).
- Note for the drafter: the outline's "hallucination as a predictable property of sampling from a language model" is supported in this form: a model trained to reproduce the statistics of text, and then sampled, will sometimes produce fluent falsehoods, at rates that can be predicted from the data (Kalai's singleton bound) and that grow with decoding randomness (Ji, conjecture). It is not established that sampling is the main cause, or that hallucination cannot be reduced. Present the strands; do not crown one. Greedy decoding does not remove hallucination: Kalai's birthday example and the GPT-4 calibration discussion concern the model's probabilities themselves.

### GND6. Why is temperature-0 output not reproducible?

- **Thinking Machines' account:** the forward pass is not "batch-invariant"; the server's load changes the batch size, which changes the order of floating-point additions inside kernels; the user sees nondeterminism (GN23). An attributed blog account (September 2025), with an experiment.
- **Vendors:** state the fact (Anthropic glossary; OpenAI `seed` "Determinism is not guaranteed"; Anthropic migration guide) but give no cause.
- Suggested wording: "In practice even temperature 0 is not perfectly repeatable. Vendors say so without saying why; researchers at Thinking Machines traced it in 2025 to servers processing many users' requests together, which changes the order of tiny rounding steps."

### GND7. In which order are temperature and truncation applied?
- Holtzman et al. (p. 6) describe temperature used "by shaping the distribution before top-k sampling".
- llama.cpp's default sampler order, as of 2026-11, applies top-k, top-p, and min-p before temperature (GN21).
- Effect (checked on the destination logits): top-k's kept set never depends on temperature (temperature keeps the ranking); the top-p set does. With p = 0.9: at T = 0.5 applied first, 2 tokens are kept; at T = 1, 3; at T = 2 applied first, 4. Applied after truncation, temperature only reshapes the 3 tokens kept at T = 1.
- Note: not a dispute, an implementation difference. The chapter should fix one order for its worked example (suggest temperature first, as Holtzman et al. describe) and say in one sentence that software differs.

### GND12. "Temperature 0" is a limit, not a computation
